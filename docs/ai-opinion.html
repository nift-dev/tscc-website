Evaluation · candid assessment

AI opinion: tscc has crossed from transpiler experiment into early compiler architecture.

What has changed my opinion most is not the headline speedup. It is that tscc added difficult runtime/module behavior without losing its regression wall, then grew a separate checker from one literal contract into durable binding, primitive types, expressions and assignments while keeping unsupported semantics explicit. That is the patient architecture a serious compiler needs.

Current verdict: I would use tscc experimentally for extremely fast TypeScript-to-JavaScript builds in a controlled codebase, especially when a separate type-check step exists. I would not yet substitute it blindly for tsc across arbitrary TypeScript projects.

The 1.4 reflects a real beginning, not broad coverage

The primitive campaign matters architecturally because it did not stop at one literal check. It now has durable program-lifetime type identity, precedence-aware expressions, assignment and const semantics, focused diagnostics, and seven promoted independent contracts. That proves tscc can grow semantic truth without teaching the parser ad hoc rejection guesses.

Type checking is the main reason TypeScript exists. A serious checker needs scopes, symbols, declaration merging, type representations, generic instantiation/inference, overload selection, assignability, control-flow narrowing, accessibility, contextual typing, lib declarations and a huge diagnostic surface. That is not “add another pass after transpilation”. It is arguably a project as large as everything tscc has built so far.

That is why the 5.6 drop-in score is much lower than the 8+ scores for modules and transpilation. A fast emitter can be excellent at its job and still not be a TypeScript compiler replacement in the sense users normally mean.

Where tscc has exceeded my expectations

The hand-written C++ architecture has remained surprisingly extensible. Early regex/source-erasure ideas evolved into explicit lexer/parser/source/diagnostic/project layers rather than collapsing under edge cases. Runtime transforms for enums, namespaces and parameter properties coexist with CommonJS and TSX instead of each becoming a separate ad-hoc preprocessor.

The performance results have also survived feature growth. In the August 2026 five-run checkpoint, tscc stayed at 1.58 ms for the small fixture, 6.83 ms for 100 basic files and 8–9 ms for the feature-heavy sets. The installed TypeScript 7.0.2 reference was much faster than older snapshots, so current ratios are lower; recording that honestly makes the performance story more credible, not less.

CommonJS changed the project category

Erasing : number is one thing. Correctly handling re-exports, cycles, default forms and live imported bindings is compiler work. The live-binding pass has had to understand shadowing in parameters, catches, blocks and loops; object shorthand versus ordinary argument lists; and template interpolations. Runtime differential testing against tsc is exactly the right way to develop that surface.

The independent regression suite may be the most important asset

The current 519 cases do more than count syntax features. They encode how we decide whether a failure belongs to parsing, runtime emission or a future semantic checker. They also prevent confirmation bias: tsc --noCheck gets to tell us that a supposedly malformed construct is actually legal TypeScript.

The checker campaign now has seven genuine semantic contracts while retaining 27 honest skips. More importantly, the semantic model, binder and durable type store are used by production checking, while static import identity also protects CommonJS live reads. That is much more convincing than flipping a switch and claiming “type checking supported”.

What should happen before a 1.0 claim

I would want substantially broader tsconfig/module-resolution compatibility, package resolution, more declaration/module corner cases, a clear source-map story, stronger diagnostics, fuzzing, and either a serious semantic checker or an explicit product definition that says tscc is a transpiler and type checking belongs elsewhere.

The latter is a legitimate choice. A world in which tscc is an exceptionally fast transpiler used alongside a separate checker can still be useful. The mistake would be leaving users unsure which contract they are buying.

Should it eventually be embedded in Nift?

I would resist making TypeScript compilation part of Nift's core architectural responsibility. Nift's rule that source-language compilation remains external is good. But distributing tscc beside Nift, documenting a build-script integration, or making installation convenient could be attractive if tscc matures. The projects can cooperate without becoming one architecture.

AI DX

tscc is highly AI-friendly in a productive sense: new language hypotheses can be turned into tiny differential tests quickly, and failures are usually reducible to explicit token/range/context decisions. Performance fixtures provide another hard oracle. That is much safer than accepting AI-generated compiler patches because they “look plausible”.

The danger is equally clear: compiler grammar has enormous long-tail complexity, and AI can generate convincing but incorrect special cases very quickly. The project's discipline of testing every discovered ambiguity against TypeScript is what makes AI acceleration useful rather than reckless.

Would I keep pursuing it?

Absolutely. The experiment has already answered the original question—yes, a native TypeScript erasure/compiler pipeline can be dramatically faster for this workload. The more interesting question now is how much TypeScript compatibility can be added before complexity or semantic work erodes that advantage.

I would rather see tscc stay explicit about its narrowly bounded checker and become excellent layer by layer than rush toward a “tsc replacement” label. The current architecture and test discipline make that patient path unusually promising.
