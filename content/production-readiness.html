Status · evidence before labels

Is tscc production-ready?

Not yet as a general TypeScript compiler. It is an unusually capable and well-tested experimental transpiler with an early semantic checker—not a safe drop-in replacement for tsc.

Candid verdict:

Use tscc for controlled evaluation, compiler research, and selected fast build paths where its exact syntax/module contract is known and an independent type-check remains in CI. Do not make it the sole correctness gate for an arbitrary production TypeScript application.

What is already credible

  • A real lexer/parser and range-based native emitter, not a regex-only syntax stripper.
  • Runtime-bearing transforms for enums, namespaces and parameter properties.
  • Relative multi-file discovery, project output layout and cycle de-duplication.
  • CommonJS lowering tested against observable tsc runtime behavior.
  • TSX preserve mode with dedicated ambiguity and malformed-input coverage.
  • A 511-case independent contract currently at 484 pass, zero fail and 27 explicit semantic skips.
  • A separate checker pass with the first bounded primitive annotation/literal contract.

Why the answer is still “not yet”

A production TypeScript compiler needs much more than valid JavaScript output. tscc still lacks a general binder, symbol model, type representation, inference, assignability, control-flow narrowing, overload resolution, declaration merging, library processing and broad semantic diagnostics.

Its project layer also has intentionally narrow relative resolution: package and node_modules resolution, path aliases, declaration files and the wider TypeScript configuration surface remain outside the current implementation.

Operational gaps under active scrutiny

Multi-file emission is currently per-file and non-transactional, so a later failure can leave earlier output behind. The supported TypeScript oracle range needs durable pinning. Native safety, fuzzing, larger real-world projects, memory measurements, cross-platform validation and reproducible release packaging all need deeper evidence before a broad production claim.

Two different milestones

Transpiler

A bounded syntax/module subset with correct runtime output, controlled rejection, reliable projects and production-grade operational behavior.

Checker

Durable syntax, scopes, symbols, types, inference and cross-module semantic diagnostics for a versioned compatibility contract.

Final goal

A production-ready type-checking compiler. The first milestone is useful, but it does not replace the second.

What would change this assessment?

A release-like candidate would need an explicit support matrix, stable failure/output policy, clean sanitizer and adversarial runs, representative real projects, reproducible benchmarks, platform/package evidence and a clearly bounded semantic contract.
