Process · AI-assisted compiler development

Fast iteration. Slow claims. Independent oracles.

AI can explore TypeScript grammar and compiler architecture at exceptional speed. That is useful only when every proposed semantic slice is bounded, compared with TypeScript where appropriate, executed when runtime behavior matters and retained as evidence in an independent suite.

The central rule:

Parser acceptance is not feature support. An AI-generated patch must survive the entire path required by its claim: syntax, structure, binding where needed, checking, lowering, emission, runtime behavior, diagnostics and malformed neighbors.

Institutional memory lives with the repositories

The compiler, independent regression suite and website each carry a root HANDOVER.md. Deeper living documents cover architecture, development, testing, decisions, roadmap and history. Together they preserve current identity, exact boundaries, implementation hazards, validation commands, unresolved questions and the reasoning behind architectural choices.

Handovers are orientation maps—not scripture. Every new developer or coding agent must reconcile them against current source, tests, Git history and observed behavior. When a checkpoint changes the truth, the relevant handover and roadmap change with it.

A vertical-slice workflow

state one narrow compatibility contract
        ↓
query tsc / tsc --noCheck deliberately
        ↓
add independent + focused tests first
        ↓
implement every required compiler stage
        ↓
inspect emitted JavaScript and diagnostics
        ↓
execute runtime-bearing fixtures
        ↓
stress scope, side effects and malformed neighbors
        ↓
run the full regression wall
        ↓
reconcile performance, docs, handovers and roadmap

The independent suite is an arbiter, not a marketing counter

The 514-case compiler-agnostic corpus asks tsc --noCheck whether syntax is accepted, uses full tsc to distinguish semantic-only failures, and runs emitted JavaScript when observable behavior is the contract. Its current 487 pass, zero fail and 27 semantic skips are categories of evidence—not a percentage-complete TypeScript implementation.

The first semantic campaign illustrates the desired migration: three previously skipped contracts are genuine passes, a binder-backed CommonJS regression protects production behavior, and 27 unsupported semantic cases remain honest skips. AI development should keep turning precisely defined gaps into owned behavior one slice at a time.

Contract-based testing: define what tscc owns

A compiler test becomes a contract test when it describes observable language or tool behavior without encoding the current parser helper, token-range layout or emitter strategy. The same case should remain meaningful if tscc later replaces a heuristic with binder identity or evolves from source edits toward richer semantic structure.

source + compiler options
        ↓
accept or reject for the documented reason
        ↓
emit the promised JS/JSX shape where shape matters
        ↓
preserve runtime behavior and module semantics
        ↓
produce stable, attributed diagnostics where required

Not every accepted program has the same contract

Syntax

tsc --noCheck says whether a form belongs to accepted TypeScript grammar; acceptance alone does not promise checking.

Emission

Erasure and transforms must produce valid output with correct evaluation order, bindings and module behavior.

Semantics

Only explicitly owned checker slices promise a type diagnostic. Other full-tsc failures remain visible semantic skips.

The contract matrix prevents category errors

Each case can state which evidence applies: parser acceptance/rejection, output constraints, runtime result, diagnostic category/location, project graph behavior or semantic-only classification. This prevents an AI assistant from “fixing” a missing type checker by teaching the parser to reject valid syntax, or from calling a transform complete because its output merely parses.

Reference behavior is queried, not worshipped blindly

TypeScript is the compatibility oracle for the intended surface, but the invocation matters. tsc --noCheck, full tsc, module mode, JSX mode, target and TypeScript version answer different questions. Contract fixtures record enough context to make the comparison meaningful, and oracle upgrades are classified across the whole suite rather than accepted case by case.

Promotion is how semantic support grows

A semantic skip is a recorded future contract, not a hidden failure. It becomes a pass only when tscc deliberately owns that language slice end to end with positive cases, negative diagnostics and relevant neighboring behavior. The primitive annotation/literal checkpoint is the model: define the boundary, implement a distinct checker path, promote exactly the covered case and leave unrelated semantics honest.

Contract changes require reconciliation

If tscc intentionally diverges from tsc, narrows a previously claimed surface or changes emitted/runtime behavior, that is not a test-only edit. The compiler contract, suite classification, README, website, handovers and compatibility/version statement must agree before the checkpoint is complete.

Testing is deliberately redundant

Focused C++

Lexer, parser and checker tests localize token ranges, structural ownership and diagnostic failures.

Runtime differential

tscc and tsc outputs are executed and compared for enums, namespaces, parameter properties and modules.

Project gates

Multi-file graphs, cycles, TSX resolution, output layout and CommonJS live bindings exercise orchestration.

Performance fixtures protect the original native-latency objective. Sanitizers, fuzzing, stress tests and real projects become increasingly important as durable syntax, binding and type state expand memory and lifetime complexity.

Why scope and side effects dominate good tests

Compiler bugs hide behind easy literals. Tests use mutation counters, calls, getters, computed properties, short-circuiting, nested functions, parameter/block/catch/loop shadowing and module cycles. A transform must preserve evaluation count, order and binding identity—not merely emit JavaScript that parses.

Checkpoints keep the long-term goal honest

The destination is a production-ready TypeScript type-checking compiler. The route is not a big-bang rewrite. Each checkpoint protects the working transpiler, adds the minimum durable structure required by a complete semantic slice, measures cost and lets the evidence determine the next abstraction.

A checkpoint is not automatically a version, release, production claim or push. Those are separate decisions. Website claims are updated only after implementation and regression evidence settle.

Where AI helps—and where it can mislead

AI is excellent at generating ambiguity matrices, shrinking failures, tracing interacting passes and keeping source, tests, website and handovers synchronized. It is also excellent at producing convincing special cases that accidentally accept invalid TypeScript or corrupt a neighboring construct. The reference compiler and executable gates are what turn that speed into engineering rather than confident guesswork.

The development philosophy:

Use AI to increase the number and quality of hypotheses tested per checkpoint. Never use it to lower the amount of evidence required to call the compiler correct.
