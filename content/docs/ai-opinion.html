Evaluation · candid reassessment · 30 August 2026

AI opinion: tscc now deserves to be judged as a bounded compiler preview.

The project has moved beyond proving that native TypeScript erasure can be fast. TSCC now owns one program graph, durable syntax and expression identity, lexical binding, canonical callable and structural types, contextual checking, arrays and tuples, relative cross-module type propagation, stable diagnostics and an explicit output contract. That is real compiler architecture. It is still a long way from general tsc compatibility.

Current verdict:

I would trial TSCC as an exceptionally low-latency compiler for a controlled project that fits its published preview matrix, while retaining full tsc --noEmit as the general semantic gate. I would not yet make TSCC the sole compiler for an arbitrary npm TypeScript application.

Why semantic checking rose from 1.4 to 4.3

The previous score described a primitive beginning. That description is obsolete. The checker now has canonical primitive, literal, union, callable, structural object, array and tuple identities; bounded narrowing; calls and arity; contextual arrow and function expressions; nested callbacks; methods and function-valued properties; interface merging and inheritance; index and call signatures; computed reads; readonly writes; and relative named-import propagation.

Just as importantly, these features did not arrive as parser rejection tricks. Durable compilation units and one program graph retain the syntax, symbols, expression children, types and diagnostics required by the checker. Cross-module types are cloned into each importing unit rather than leaking unit-local identities across ownership boundaries.

That is enough semantic substance to call TSCC a compiler preview rather than merely a transpiler with one experimental check. It is not enough to approach full TypeScript: generic instantiation and inference, overload resolution, class semantics, declaration libraries, broad control-flow joins, standard-library types, package typing and much of contextual inference remain absent.

Why the drop-in score fell from 5.6 to 3.5

The old score conflated “broadly useful emitter” with “drop-in replacement.” Evidence has made the distinction sharper. A real application depends on more than language syntax: node_modules and package resolution, path mappings, declaration files, standard libraries, project references, source maps, watch/incremental builds, a much wider tsconfig surface and diagnostic compatibility all matter.

TSCC can be excellent within its frozen ES2022, relative-module, preserve/esnext/commonjs and JSX-preserve contract while still scoring modestly as an arbitrary tsc replacement. Lowering this score is not loss of confidence. It is a better definition of the question.

The bounded preview is a meaningful milestone

The TCP0-TCP5 candidate passes 555 cases, fails zero current-scope cases and retains 24 intentional semantic skips across a 579-case independent corpus. A frozen module-free source also compiles through production TSCC and returns the explicit expected result 42 under Node and JS++ at 7/7.

The candidate adds deterministic diagnostics and outputs, two documented emit policies, frozen positive and negative projects, ASan/UBSan, 400 deterministic malformed mutations, representative-project evidence, a loose startup guardrail and reproducible archives. These gates make “preview” an executable contract rather than a mood.

Important boundary:

555/0/24 is not a TypeScript-completeness percentage. The 7/7 runtime intersection is not JS++ module support. A qualified Linux preview is not a stable cross-platform release.

Architecture is now one of the strongest parts

The most encouraging design decision is not any individual feature. It is the repeated replacement of temporary parallel paths with owned compiler structure: one ProgramGraph, durable CompilationUnit state, stable syntax identity, decomposed annotation parsing, canonical types and retained statement-expression roots.

The hybrid emitter is also pragmatic. Semantic structure owns meaning where TSCC checks or rewrites behavior, while validated source edits preserve unchanged JavaScript bytes. A wholesale AST-printer rewrite is not automatically more correct, and would put both compatibility and latency at risk before the semantic model is ready to justify it.

The regression suite remains the project’s most valuable asset

The 579 cases are useful because they classify evidence, not because 579 is a large number. tsc --noCheck arbitrates syntax, full tsc distinguishes unimplemented semantics, Node checks runtime behavior, and explicit expectations prevent matching wrong outputs from counting as success. Every promoted slice carries positive behavior and negative diagnostics.

The 24 skips are a strength. They stop parser breadth from masquerading as type-checker breadth and provide a visible queue of semantic contracts that have not yet been earned.

Today’s red CI is an orchestration warning, not a compiler regression

The current Linux and macOS GitHub jobs fail before the compiler tests because make test invokes ../tscc-regression-suite/validate_preview_contract.py, while the workflow checks out only the TSCC repository. Windows runs the smaller test-core target and passes. The failure therefore does not contradict the recorded local preview results, but it does mean the public CI configuration cannot currently reproduce the aggregate evidence it claims to run.

This matters. Multi-repository tests are production dependencies of the evidence system even when they are not production dependencies of the compiler. CI must either check out the pinned sibling suite, consume a versioned suite artifact, or separate self-contained core tests from an explicitly provisioned aggregate gate. A green local workspace is not enough if a clean checkout cannot discover its required evidence.

That is why CI/release readiness is 6.5 rather than inheriting the regression-discipline score. The testing ideas are excellent; their clean-checkout automation still needs repair and a successful rerun.

What should happen next

  1. Repair the CI topology and prove Linux, macOS and Windows from clean checkouts without weakening the aggregate contract.
  2. Run PC0V external Valgrind confirmation on Nick’s Ubuntu machine and retain exact evidence.
  3. Use TCP6A to classify pinned real small projects before choosing more language breadth.
  4. Let those failures choose between package resolution and broader cross-module type propagation.
  5. Keep benchmark work equivalent and reproducible as checker cost grows.

Should it eventually be embedded in Nift?

No, not as a core responsibility. Nift’s source-language compilation boundary remains sensible. TSCC can be distributed beside Nift and documented as an external build tool without making either project architecturally dependent on the other.

Would I keep pursuing it?

Absolutely. TSCC has already shown that checkpointed AI-assisted work can grow a fast native transpiler into coherent compiler architecture without pretending the destination has arrived. The next phase should be less about accumulating checkpoints and more about clean CI, real projects, packages, external memory evidence and allowing actual adoption failures to choose the next vertical slices.
